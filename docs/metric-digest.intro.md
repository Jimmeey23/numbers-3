# Atlas — metric digest

Every metric the app shows, what it reads, how it is calculated, and what it reads right now.

Produced by auditing each source spreadsheet against the metric registry on 2026-10-04. The
reference section below is generated by `scripts/make-digest.mts` from the registry and from live
values captured by `scripts/audit-sources.mts`, so it cannot drift from the code: regenerate it
and it tells you what the app actually does today.

---

## 1. How to read this

Atlas has one metric registry, `src/semantics/metrics.ts`. Nothing on any tab computes a number
for itself — a tab names a metric id, and the registry owns the formula. That is why the same
question gives the same answer on every tab, and it is why this digest can be complete: there is
exactly one place where a metric can be defined.

Each metric declares four things that matter here:

| | |
|---|---|
| **Grain** | the table it runs on — one row of what |
| **Reads** | the source columns, named exactly as the spreadsheet names them |
| **Aggregation** | `sum`, `ratio of sums`, `mean of rows`, `median`, `count`, `distinct count`, or `custom` |
| **Coverage** | the share of rows that could contribute, when some cannot |

**On rates.** A rate is never an average of rates unless the source column is itself a per-entity
rate. `Fill rate` is `SUM(attended) / SUM(capacity)`, not the mean of each class's fill — those
differ whenever class sizes differ, and the second is wrong for a studio total. Where a mean of
per-entity rates is genuinely wanted, the metric says so in its name (`Avg sessions used`,
`Cancellation rate (per member average)`).

**On nulls.** Null means unknown, never zero. A metric returns null rather than 0 when nothing
could be computed, and the card shows an em dash. A rate whose denominator is zero is null, not
100%.

**On coverage.** When a metric can only be computed on some rows — a utilisation figure needs a
session cap, a conversion span needs a conversion — the card shows what share contributed. A
figure computed on 11% of memberships is still correct; it is just about 11% of them, and the app
says so rather than letting you assume otherwise.

## 2. The sources

Nine spreadsheet tabs across six spreadsheets. Row counts are from the audit run.

| Sheet | Grain — one row per | Rows | Used for |
|---|---|---|---|
| **Checkins** | check-in | 149,680 | attendance, the member side of the visit grain |
| **Bookings** | booking | 211,595 | booking lifecycle, cancellations, lead time |
| **Sessions** | class occurrence | 25,470 | capacity, fill, attributed class revenue |
| **Recurring** / **Teacher Recurring** | recurring slot / trainer slot | 1,144 / 3,277 | pre-aggregated slot summaries (loaded, not currently read by a metric) |
| **Sales** | sale **line item** | 24,846 | revenue, discounts, product mix, membership balances |
| **New** | new client | 21,105 | acquisition, conversion, LTV, retention of first-timers |
| **Lapsed** | membership interval | 28,986 | churn, utilisation, risk, liability |
| **Payroll** | trainer × month | 1,117 | trainer economics, cost, contribution |
| **Leads** | enquiry | 25,194 | pipeline, response time, win rate |

Every sheet's header was fetched and compared against the schema the app declares. All nine match
on every declared column. Three carry undeclared extras the app ignores: `Payment Item` on Sales,
and blank trailing columns on New, Payroll and Checkins.

### Grain traps, and what the app does about them

**Sales is a line-item feed, not a transaction feed.** The grain is `Sale Item ID`. A three-item
basket is three rows. The naming convention is the guide: a column prefixed **`Sale Total …`** is
sale-level and identical on every line; everything else is per line. Measured on the live sheet:
24,426 of 24,609 rows carry a `Payment Value` within 2% of `unit price × quantity`, and of 1,699
multi-line sales not one has equal payment values across lines with differing unit prices — which
is what a repeated total would look like. So `Payment Value` and `Payment VAT` are **summed**
across rows, while `Sale ID` is used to count transactions.

This was wrong until 2026-10-04 and is the one material correction this audit produced — see §4.

**A membership's own columns repeat across the lines that sold it.** `Sec. Membership Money Left`
is a balance, not a payment; two lines of one sale both carry it. Metrics over those columns
count once per `Sec. Membership ID`, not once per row and not once per sale — a sale that sells
two memberships must count both, and 190 sales do.

**The visit grain is built, not read.** Neither Checkins nor Bookings alone answers "did this
person attend". Checkins knows attendance and payment; only Bookings knows about cancellations
made before the penalty window. The app reconciles them into a `visits` table keyed on
`date | time | member`, on the reasoning that a member cannot be in two classes in the same
minute — the sheets' own `UniqueID` columns do not match across sources. A check-in row with no
member id cannot be matched, so it is kept as its own unresolved visit rather than dropped.
Every row records `in_checkins` / `in_bookings`, which is what the source-agreement metric reads.

## 3. What was checked

Four passes, all re-runnable: `npx tsx scripts/audit-sources.mts`.

| Pass | Question | Method |
|---|---|---|
| **A** | Does every column a metric names actually exist? | Fetch each sheet's real header; match all 445 `sources` claims against it |
| **B** | Does every metric compute? | Run all of them over 90 days of live data; record value, sample size and coverage |
| **C** | Is the value in range? | A percent outside 0–100%, a negative count, a figure on under a quarter of rows that does not declare coverage |
| **D** | Is anything double counted? | For each sheet, find columns identical on every row of an entity, then flag any metric that `SUM`s one |

Three more audits run alongside and are part of the build: `audit.mts` (registry invariants),
`audit-new.mts` (18 arithmetic fixtures), `audit-bindings.mts` (one concept, one metric, across
tabs).

## 4. What the audit found, and what was done

Nineteen high and eleven medium findings on the first run, plus one more that no check caught — it surfaced from reading the generated reference table, where two metrics about the same thing sat four rows apart and disagreed thirtyfold. Each was checked by hand against the
sheet before anything changed — four of the nineteen were the audit being wrong, and saying so is
part of the result.

### Real, and fixed

**1 · Sales revenue was understated by 10%.** `Payment Value` was collapsed to one value per
`Sale ID` — the largest line — on the belief the export repeats a sale total. It does not. This
discarded **₹77.5L of ₹15.88Cr all-time**, and ₹5.9L of ₹59.5L in September 2026 alone. Money
columns now sum across rows. Verified against the raw CSV: gross ₹59.54L, VAT ₹2.84L, net
₹56.70L, all three matching to the rupee.

**2 · Three Lapsed columns are present but never populated.** `No Shows`, `Days Frozen` and
`Discount Value` each hold `0` on all 29,068 rows. The metrics over them —
`l_no_shows`, `days_frozen`, `l_discount_rate` — reported a confident zero, which reads as
"there were none" when the truth is "the export does not record this". The loader now detects an
all-zero column and marks the dependent metrics unreliable, so the card carries the caveat. The
detection is by measurement, not a hard-coded list, so a column that starts being filled stops
being flagged without a code change.

**3 · `refund_rate` read a column that does not exist.** The Bookings sheet has no `Refunded`
column, so the metric was permanently 0%. Removed — `voided_rate` on Sales is the real answer.

**4 · `p_retention_of_converted` read 129%.** Added four days ago from the reference app's
definition (Retained ÷ Converted), it cannot be computed on this export: the Payroll sheet's
`Retained` is **not** a subset of its `Converted`. On 441 of 1,117 trainer-months, Retained
exceeds Converted — Pranjali Jain, Feb-2024: New 18, Converted 6, Retained 10. Both are
independent outcomes of the New cohort. Removed. `p_retention_rate` divides by `New`, which does
hold: `Retained ≤ New` and `Converted ≤ New` on **every** row.

**5 · LTV was counted twice for 181 members.** `Ltv` is a member-level lifetime figure, and 181
of 20,924 members carry two New rows — a second first-visit record — which repeat it.
`total_ltv` now counts one Ltv per `Member Id`.

**6 · Eight metrics cited a column name the sheet does not use.** Seven named
`Completed Sessions`; the Lapsed header says `Total Sessions Completed`. Two named a
`Sale Id` column the Bookings sheet does not have. The *code* read the right field in every case
— the normaliser already handles both spellings — so no number was wrong, but the provenance
shown in the app's own definition popout was. Corrected.

**7 · The late-cancellation rate read 0.6% instead of roughly 15%.** Found by reading the
generated reference table rather than by a check: `v_late_cancels` counted 2,833 late
cancellations over 90 days while `v_late_cancel_rate` reported 0.6% of a base of ~15,600 — about
94. Two metrics about the same thing, 30× apart.

In the Bookings sheet, `Cancelled` is a **superset** of `Late Cancelled`. Across all 211,595
bookings:

```
Cancelled AND Late Cancelled   29,099
Late Cancelled only                 0      ← never set on its own
Cancelled only (ahead)         24,134
neither                       158,362
Attended                      157,827      none also flagged Cancelled
No Show                           535      none also flagged Cancelled
```

The app's `cancelled` field means "cancelled ahead of the penalty window" — show-up rate, no-show
rate and late-cancel rate all exclude it from their base, and their descriptions say the three
sum to 100%. Taking the raw flag put every late cancellation outside that base *and* nulled the
late-cancel numerator, because a late cancel is always also `Cancelled`.

`cancelled` is now `Cancelled AND NOT Late Cancelled`, and a booking row's late-cancel flag is
taken as authoritative over the check-in's. This moves `v_cancel_rate` down and
`v_late_cancel_rate` up, on the Bookings, Late cancellations and Format comparison tabs.

**8 · Ten metrics computed on a minority of rows without saying so.** A figure over 11% of
memberships is not wrong, but the card should say which 11%. All ten now declare coverage and a
reason.

### The audit was wrong — and was corrected

Four flags were false positives. Finding them is why every flag was checked against the sheet by
hand before anything was changed; the checker was then tightened so it does not repeat them.

**`Sale Item Quantity` is not a sale-level column.** The audit flagged `units`,
`discount_value` and `category_revenue` for summing it. It is near-constant: `1.00` on 24,600 of
24,846 rows, `2.00` on 18, blank on 228. Identical within a sale because almost every quantity is
1, not because it is a sale total. Summing is correct. Pass D now requires a column to vary
*between* entities as well as repeat *within* one, and reports a near-constant column separately.

**`Discount Value In Currency` genuinely is sale-level**, and the pipeline already knew: it is
allocated across the sale's lines by post-discount list value, and only when no item-level
discount exists. The flag was right about the column and wrong about the metric. Pass D now
carries an explicit, documented exemption for metrics that allocate rather than sum.

**Two "double count" flags were the empty columns above.** `No Shows` and `Days Frozen` were
flagged as member-level repeats; they are identical on every row because every row is `0`. Pass D
now reports an all-zero column as what it is — present but never populated — which is the
finding that matters.

**A structural null is not a defect.** `survival_90` is null over a 90-day window because it
needs a first visit at least 90 days old; the window barely contains any. A metric that declares
coverage and returns null for that reason is no longer flagged.

### Noted, not changed

**`Price Excluding VAT In Currency` is a sale-level column.** An existing Data-health defect calls
it a data error because it exceeds payment-minus-VAT on some rows. The audit explains why: on a
multi-line sale it holds the whole sale's net while the line holds the line's. It is read only for
that check, never summed, so no metric is affected — but the defect's wording is now known to be
describing a grain difference rather than a bad value.

**`Sessions Used %` is blank on 25,677 of 29,068 Lapsed rows (88%)**, and `Sessions Limit` is
blank or "Unlimited" on 76%. This is why utilisation metrics report 11% coverage. The data is
genuinely absent, not mishandled.

## 5. Worked examples

Six metrics where the arithmetic is worth seeing, all on real figures.

### Gross revenue — why the grain matters

Sale `322957430`, 5 September 2026, two line items:

```
₹13,125.02   Studio 8 Class Package
₹    74.98   Money Credits
─────────────
₹13,200.00   the sale
```

`Payment Value` is per line, so gross revenue adds both. Counting once per `Sale ID` kept
₹13,125 and lost ₹75. Across September that pattern cost ₹5.9L.

```
gross_revenue  = SUM(Payment Value) where not voided        = ₹59.5L
transactions   = COUNT(DISTINCT Sale ID)                    = 874
aov            = 59.5L / 874                                = ₹6,813
```

Note the division: the numerator sums **rows**, the denominator counts **sales**. Both are right,
and they are not the same grain.

### Fill rate — a ratio of sums, never a mean of ratios

Three classes: 12 of 20 seats, 3 of 6, 18 of 20.

```
ratio of sums:  (12+3+18) / (20+6+20)  =  33/46  =  71.7%     ← what the app reports
mean of ratios: (60% + 50% + 90%) / 3            =  66.7%     ← wrong for a studio total
```

The second gives the six-seat class the same weight as the twenty-seat one. The gap widens
exactly when class sizes differ most, which is when you most want the number.

### Churn — the denominator is the whole argument

September 2026:

```
churn_rate         churned / every membership in scope       = 16.4%
churn_rate_ending  churned / memberships whose term ended    = 28.1%
```

Both are in the app. The second is the actuarially correct reading: a membership that does not
expire this month had no opportunity to churn in it, so including it in the base only dilutes.

### Retention — same trap, opposite direction

```
retention_rate          Retained / all new clients      = 12.9%
retention_of_converted  Retained / converted clients    = 84.2%
```

A six-fold difference from one choice of denominator. "Do the people who buy stay?" is the second
one.

### The acquisition funnel — two sheets, two clocks

September 2026: 621 leads created, 391 first visits. More first visits than the lead stage used to
show, which looked impossible. Joining the two sheets on member id, email and phone explains all
391:

| | people |
|---|---|
| Inside the trial stage as the Leads sheet recorded it | 209 |
| Never appear in the Leads sheet at all — walk-ins, guests, referrals | 68 |
| Lead row exists, but created in another month | 49 |
| September lead row that does not record the trial or visit | 65 |

The funnel's trial stage is now read from the New sheet, so it equals first visits by
construction, and the one remaining cross-sheet step — 621 enquiries to 391 first visits — is the
only place the two clocks meet.

### Late cancellations — one flag inside another

The Bookings sheet sets `Cancelled` on every late cancellation as well. Reading it literally put
them outside the base of every booking-outcome rate, and nulled the late-cancel numerator:

```
                      before      after
cancelled ahead        6,161      3,437
cancel rate            29.1%      16.2%
late-cancel rate        0.6%      15.4%     ← the number that was wrong
show-up rate           99.1%      84.4%
                                  ──────
show-up + no-show + late-cancel   100.1%    (rounding)
```

The three rates share one base — bookings that reached the class — which is why they sum to 100%
and why an error in one of them is visible in the others.

### Format comparison — the residual bucket

`PowerCycle` and `Strength Lab` are matched by name; **everything else is Barre**. That is a
deliberate residual, not a guess, and it is what makes the formats sum to the total:

```
611 Barre + 200 PowerCycle + 109 Strength Lab = 920 = visits
```

A non-exhaustive rule silently dropped the unmatched classes, which is why this tab used to
disagree with Attendance.

## 6. What this digest does not cover

**Same-day cancellations.** Neither source records a cancellation timestamp. A metric built from
`lead_time_days` would report "booked on the day and later cancelled" under the label "cancelled
on the day". It was written, found to be mislabelled, and deleted. It needs a `Cancelled At`
column.

**Penalty revenue.** No `Charged Penalty Amount` column exists in the Check-ins export.

**Recurring and Teacher Recurring** are loaded and health-checked but no metric reads them; their
pre-aggregated slot summaries duplicate what the app computes from Sessions.

**62 metrics are defined but not bound to a tab.** They are reachable through the agent API and
the widget builder, and several exist only as reconciliation variants that Data health compares —
see `src/semantics/concepts.ts`. A metric appearing in the reference below with
_not bound to a tab_ is one of these, not a broken one.
